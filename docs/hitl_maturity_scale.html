Understanding Working-Relationship Progression

Why the framework tracks a working relationship, not a maturity score — and what that has to do with the five pattern types

This page replaces the earlier HITL Maturity Scale (M1–M5)

The framework used to describe human involvement as a five-point maturity curve — M1 through M5 — derived from an activity's pattern type. That model is retired. Every activity now carries a real working-relationship classification instead: Current State, Future State, and a Progression Ceiling. Pattern type hasn't gone away — it still identifies what kind of work an activity is, and still drives the site's visual system — it's just no longer the thing a maturity number gets derived from. See the full Working-Relationship Progression Methodology for the underlying design work and pilot findings.

Start Here: Design, Not Safety

Most people's first association with "human-in-the-loop" is safety — keeping a person in the chain to catch AI errors before they cause harm. That's correct, but it's not the whole idea, and it's not what this page is about.

HITL Design vs. HITL Safety

HITL Safety asks: where must humans stay involved to prevent harm? HITL Design asks: where should humans stay involved to produce the best outcome? The design question is broader, more strategic, and it's the one this framework is built around.

Framed as a design question, human involvement isn't something that just happens to a process as AI tools get adopted — it's something an organization can decide, deliberately, activity by activity. Working-relationship classification is how that decision gets named and tracked.

The Three Layers Every Process Sits In

Every piece of enterprise work belongs in one of three layers:

Human Layer
Judgment & Oversight		Approvals, interpretation, escalations, ethical decisions — the work that requires wisdom, context, and accountability.
Automation Layer
Execution		Routing, matching, scheduling, orchestration — rules-based workflows that are consistent, reliable, and repeatable.
AI Layer
Prediction & Generation		Drafting, summarizing, pattern detection, forecasting — fast, scalable, tireless processing and generation.

The most common failure in human-AI operating model design is work sitting in the wrong layer — humans doing Transaction work that automation should handle, or AI generating outputs for Decision work where human judgment and accountability are non-negotiable. Working-relationship classification is how the framework now names which layer an activity actually sits in, activity by activity. Full detail in the HITL Design Methodology →

The Working-Relationship Ramp

Six ordinal categories, read left to right as increasing automation. Every classified activity sits on exactly one of these today — its Current State.

Human-only
Judgment
Oversight
Augmentation
Agent-delegation
Automation

Darker = more human. Progression moves one adjacent step at a time — skipping a category isn't modeled.

CategoryWhat it means
Human-onlyNo meaningful AI role, by design — legal, ethical, or relational reasons hold regardless of how capable the technology gets.
JudgmentA person makes the actual call. AI's role is informational only — it can supply data or a ranking, but the reasoning and decision are the person's.
OversightAI performs or proposes the work; a person reviews and approves each instance before it takes effect.
AugmentationA person remains the primary actor and does the work; AI assists — drafts, suggests, summarizes — but doesn't act on its own.
Agent-delegationAn AI agent performs the work autonomously within policy bounds; a person handles only flagged exceptions, not every instance.
AutomationAI performs and completes the work with no person in the loop for that instance.

Current State, Future State, Progression Ceiling

Instead of a five-point curve, each classified activity carries three values:

TermDefinition
Current StateThe activity's real working-relationship category today.
Future StateThe category actively being pursued as the near-term target. May sit below the Progression Ceiling by deliberate choice.
Progression CeilingThe most-automated category this specific activity can plausibly reach, for technical or governance reasons. May equal Current State — i.e. no further runway, either because the activity is already fully automated or because it's already at its human-side ceiling.

A positive gap between Future State and Current State is the AI convergence opportunity. A Progression Ceiling that equals Current State isn't unfinished work — for a lot of judgment- and accountability-carrying activities, that's the design succeeding, not stalling.

How the Progression Ceiling Guards Judgment

This is the mechanism that does the same job the old M3 design-intent target used to do, but per activity instead of per generic pattern curve — and it's the piece most worth understanding, because it's what actively protects certain work from drifting toward Automation the way routine processing does.

  1. Automation is always the floor. An activity's Current State is never below where it already runs autonomously; its own future ceiling starts there.
  2. A standing accountability duty makes Judgment the ceiling. Strategic authority, EEOC/adverse-impact liability, ERISA fiduciary duty, NLRA/union exposure, or confidentiality/duty-of-care obligations put a hard ceiling at Judgment — no further automation is modeled past that line, regardless of pattern type.
  3. For everything in between (Agent-delegation / Augmentation / Oversight): if the activity's own note flags a standing duty attached to that specific tier, that tier is the ceiling. If no such duty is flagged, the ceiling moves one notch more automated.

The practical effect: two activities can sit at the same Current State today and still have completely different runway ahead of them — not because one was assessed more generously, but because the accountability actually attached to the work is different. A shallow gap between Current State and Progression Ceiling on a Judgment-tier activity isn't an unfinished assessment. It's the ceiling correctly holding the line on work that shouldn't automate further.

Where Pattern Type Still Matters

The five work-pattern types — Decision, Knowledge, Document, Transaction, Exception — haven't been retired. They still answer a real question: what kind of work is this, fundamentally, and they're still recorded against every activity. What's changed is visibility: pattern type is maintained data, not a displayed view. It no longer appears as the framework's classification lens on any page — Working-Relationship classification is what the framework shows.

What's changed is what pattern type is for. It used to be the source a generic H% decay curve was derived from — every Decision-pattern activity inheriting the same M1→M5 trajectory whether or not that trajectory actually fit it. Now it sits in the background as descriptive metadata alongside a real, individually-assessed Current State / Future State / Progression Ceiling — available for internal reference, not part of what any view surfaces. Two activities of the same pattern can — and often do — carry different real classifications once assessed on their own facts.

A Real Example

7.2.1.3 (Approve job requisition — pattern Decision) and 7.2.4.3 (Hire candidate — pattern Transaction) carried very different pattern-derived numbers under the old model, yet both turned out to be the same real working relationship — Oversight, a human checkpoint on each instance — once classified by what actually happens rather than by pattern label alone.

Reading the Numbers

When you see a working-relationship classification anywhere in this framework, it's worth reading the ceiling logic behind it, not just the category name:

  • Current State sitting well below the Progression Ceiling usually means real, near-term AI convergence opportunity — automation the work can plausibly absorb
  • Current State equal to the Progression Ceiling at Judgment or Human-only isn't a design failure — it's the design correctly holding the line on judgment-critical or accountability-carrying work
  • An open/undecided Progression Ceiling means the runway is a real, unresolved governance question — not a gap in the assessment
  • Future State set below the Progression Ceiling by choice is a deliberate pacing decision, not evidence the activity is under-optimized

A Note on Where This Comes From

Working-relationship classification is individually assessed against real process data and RACI assignments, not derived from a generic pattern curve — where it has been done (PCF 7.0's HR domain, built out first), the classification reflects the actual activity, not an estimate. Domains not yet individually assessed still show their pattern-type reference as a starting point, the same way the original methodology always intended pattern type to work before organizational data was available — see the HITL Design Methodology for how pattern types are defined and assigned, and the Working-Relationship Progression Methodology for the full design work, the Progression Ceiling logic, the readiness gate, and the pilot findings this page draws from.
