Content Promotion Policy — Sandbox / WIP / Production

Three explicit tiers and a status ladder so a piece of content can't silently drift between exploration, review, and the live site
Documentation Dashboard Work in Progress
Concept stage — not yet part of the framework. A process/governance proposal, not a content or design change: it doesn't alter what's on any live page, only how a change earns its way from an idea to something shipped.
Related Requirements — Requirements Register
  • GR-045 — define an explicit content-promotion pipeline (tiers, status ladder, checklist, changelog) so changes can't silently drift between sandbox, WIP, and production

Why this exists

On September 21 the tagline on hitldrivenarchitecture.com turned out to exist in three different wordings across the live site, the sandbox, and the WIP catalog — with no record of which one was ever deliberately "shipped." Pulling the thread further: Rule 1's Token Lock was missing colors that had been live for weeks before anyone caught it, and GR-002 through GR-011 all sit at "rule exists, not confirmed swept" because no one has gone page-by-page to check.

None of this is one bad file. It's the predictable output of a system with no promotion pipeline and no drift-detection step. Content already moves between three informal spaces — sandbox exploration, WIP review, and the live production site — but nothing marks the boundary between them, nothing requires a deliberate act to cross it, and nothing records that a crossing happened.

This doc defines three explicit tiers, extends the Proposed → Under Review → Concept Agreed → Text Approved → Adopted status ladder GiGi proposed for the collaboration docs to cover content promotion (not just principles), and proposes a lightweight production changelog so the next drift shows up as a diff instead of six weeks later, by eye.

The three tiers

TierWhat it's forWhat it is NOT
Sandbox (e.g. docs/sandbox/pcf7.html)Free exploration — trying layouts, copy, structure with Tim and GiGi before anything is committed to an ideaNot reviewed, not voted on, not a staging step. Nothing here is assumed correct or final, and nothing auto-flows out of it.
WIP (the WIP catalog / requirements register)Candidate content that's been proposed and is being reviewed or voted on"Approved" in WIP is a review outcome, not a publish event. It does not push anything to production by itself — someone still has to pull the file and commit it.
Production (hitldrivenarchitecture.com, source of truth in Tim-King2643/HITL-Framework)The live, publicly reachable siteThe only tier where changes are tracked (see the changelog below). Nothing is "production" until it has actually been committed to the repo and deployed — a WIP item marked Approved is not yet production.

Today there is no enforced boundary between these — a wording can drift from sandbox into what people treat as settled without ever passing through WIP review or a recorded production commit. The status ladder below is how a piece of content earns its way from one tier to the next, on the record.

Status ladder, applied to content

GiGi's ladder for the collaboration docs — Proposed → Under Review → Concept Agreed → Text Approved → Adopted — maps onto the three tiers with one addition at the end, since content also has to actually land in the repo and go live:

StatusTierWhat it means
ProposedSandboxAn idea or draft exists; not yet reviewed by anyone else
Under ReviewSandbox → WIPMoved into the WIP catalog for comment/voting
Concept AgreedWIPThe direction is agreed; wording may still change
Text ApprovedWIPThe exact text/asset is signed off as ready to ship
AdoptedWIPFormally accepted as the version that should go live — this is what "Approved" in WIP should mean going forward
PublishedProductionActually committed to the repo, deployed, and logged in the production changelog
The key fix: Adopted ≠ Published. An item can sit at Adopted indefinitely without being live, and that's fine — but nobody should describe it as "done" until it clears the last step. This is exactly the gap that let the tagline drift: it was effectively treated as agreed-on in more than one place without ever being tracked through to a single Published version.

Promotion mechanics

Who moves things: Tim is the only one who commits to production (via the GitHub web editor or desktop, as today). Claude prepares the change and verifies it landed; Tim and GiGi both weigh in during WIP review, but promotion to Production is a single deliberate act Tim takes, not something that happens by consensus alone.

What triggers a move between tiers:

  • Sandbox → WIP: Tim or GiGi decides an idea is worth formal review and it gets added to the WIP catalog.
  • WIP → Adopted: review/voting concludes and the exact text or asset is signed off.
  • Adopted → Published: Tim pulls the adopted file, commits it to the repo, and the change is deployed.

What a promotion requires (checklist), before marking anything Published:

  1. The adopted version is the one actually committed — no last-minute rewording outside the record.
  2. If the same value (tagline, color token, rule text) appears in more than one file, every occurrence is identified and updated together — not just the one file that prompted the change.
  3. The commit is verified live (e.g. via raw.githubusercontent.com or the deployed page itself), not assumed from the commit alone.
  4. An entry is added to the production changelog (below) before the task is considered closed.

This checklist is deliberately short. The goal isn't heavy process — it's making the "did this actually ship, and everywhere it needed to" question something the record answers, instead of something someone has to remember to ask.

Production changelog

A single file in the repo — CHANGELOG.md at the root, or docs/production-changelog.md — with one row per shipped change:

## 2026-09-21 - **Tagline locked** across header, footer, and meta description to: "<final wording>" Files touched: index.html, /about/index.html, /footer-partial.html Source: Adopted from WIP item #<id> Verified: raw.githubusercontent.com + live page, 2026-09-21

Each entry needs: the date, a one-line description of what changed, the list of files touched (this is what would have caught the tagline drift — a reviewer scanning past entries would see the tagline touched three files, not one), which WIP item (if any) it came from, and confirmation it was verified live.

This doesn't need tooling to start — it's a markdown file Tim edits by hand alongside each production commit, or Claude drafts the entry and Tim commits it with the change. If it proves useful, it could later gate merges (a PR template field) or feed a lightweight drift-check script that diffs a tracked value like the tagline across all files that should contain it.
