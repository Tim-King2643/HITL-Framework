H% Provenance Badge

A naming and placement standard for the Maturity Table's H% figures — every state is modeled, distinguished by how well-grounded the model is
Documentation Dashboard Work in Progress
Related Requirements — Requirements Register (GiGi’s evaluation docs)

  • GR-014 — define H%'s unit of measure everywhere it's displayed (Implemented in Sandbox 7.0, awaiting approval vote — see Unit of Measure below)

Why This Now

Tim saw a CHRO Office Substack dashboard example tagging compensation figures “DIRECTIONAL” and “AI-INFERRED — FROM DIRECTIONAL P50” with a sources link, and liked the pattern of surfacing data provenance visibly rather than in a footnote. GiGi had separately flagged, in her September 3 review, that H% needs precision about whether it's modeled or observed — exactly what Rule 14 and Rule 16 of the unified Framework Content Generation Rules already require. This standard is the concrete mechanism that satisfies both.

The Problem

Right now every domain's H% figures render identically, with no visual signal that they rest on very different footing. Some domains carry RACI-grounded pattern assignments traced to real APQC L4 activity text; others carry draft M1–M5 values that have never been run through that validation pass — yet a reader looking at any Maturity Table today has no way to tell the two apart. The badge this proposes is per-domain, not per-row: every row within one domain's table already shares the same status, so tagging each row individually would just be redundant.

The Recommendation

A status chip in the panel's top-right corner, next to the table title, plus a “sources ▾” link that expands into the existing “Note on Where the Numbers Come From” methodology text at the point of use — rather than leaving it in a separate document. Two alternatives were sketched and set aside: a header-only chip with no expansion, and badging the M1/M3/M5 column headers directly (solves scroll-visibility, but adds a redundant sixth column for a value that's constant per domain).

Proposed Tokens

These are new badge-text tokens, not new colors — the chip styling reuses the already-locked amber/navy pair, so nothing here touches Rule 1's locked color set. The wording matches the house style already locked in on the WIP ribbon (“Draft — Not Yet Part of the Framework”) and the RACI table's own footer (“RACI grounded in real APQC L4 activity text”): ALL-CAPS keyword, em dash, plain-language qualifier. “MODELED” is the umbrella word on every state, since nothing in the framework today is empirically observed — every H% figure is a reasoned estimate, whether from a generic pattern-type reference or from real RACI assignment against actual activity text. The qualifier carries the real distinction: how well-grounded that model is, not whether it's a model at all. “Observed” is deliberately reserved, unused until the framework ever ingests genuinely measured data (real time-tracking, an employee survey) — the same distinction the CHRO Office example draws between real (if paywalled) market survey data and a derived, AI-inferred chart built on top of it.

Unit of Measure — Sandbox 7.0 Implementation

The sections above answer one question about an H% figure: how well-grounded is the model behind it? GiGi's review asked a second one (GR-014): if an activity is “65% human,” 65% of what? Until now the framework had no answer. This section defines the unit and the design items that put it at the point of use in Sandbox 7.0 (docs/sandbox/pcf7.html). The scope is Sandbox 7.0 only. Production is out of scope until a full production update.

Implementation Design Items

IDItemSpecification
U1Unit definitionH% is a modeled index of how much control over each instance of the work stays with a person. It counts direct execution, review, approval, and oversight, and excludes work that runs with no person in the loop. It is explicitly not a share of hours, effort, or FTE, and not a headcount estimate (consistent with Rule 16 and GR-008).
U2Anchor scaleEach activity takes the fixed value of its working-relationship category: Human-only 95, Judgment 82, Oversight 62, Augmentation 48, Agent-delegation 28, Automation 10. Claude modeled these values as an ordinal scale, in roughly even steps with the ends pulled in from 0 and 100. They have not been calibrated against observed data, and that disclosure appears wherever the values are shown.
U3Rollup ruleA process (L3) value is the plain average of its activities’ anchor values. A leaf L3 with no L4 activities takes its own category value. A role value is the equal-weighted average of the processes the role is Accountable for. Activities classified Open / undecided are left out, since they carry no value yet.
U4MODELED chipA MODELED chip sits in front of every Current State and Progression Ceiling % H value: process rows, People View role rollups, and the Readiness Gate table. It is one chip per value, not one per column, so a screenshot of any single row still carries the label. The chip reuses the sandbox’s existing provenance-chip style, so no new colors are added (Rule 1).
U5Info boxClicking the chip, or pressing Enter/Space on it, opens the sandbox’s standard info box: the same panel, × close, and click-outside-to-close behavior as the Consequence-of-Error and Progression Ceiling checklists. Only one box is open at a time. It shows the unit (U1), the anchor scale with its calibration note (U2), and that row’s actual arithmetic, computed live from the classification data (U3).
U6Display precisionValues display as whole numbers (27.7% → 28%). One decimal on an average of modeled anchor values implied a precision the number doesn’t have (Rule 14). The info box shows the unrounded working so the rounding is visible.
U7LegendOne line in the sandbox legend: “Every % H is a modeled index, not measured data — click the chip for what it measures and how that row was calculated.”
U8ScopeSandbox 7.0 only. Production pages are not referenced or changed. They move with the full production update.

How This Relates to the Provenance Tokens

In Sandbox 7.0 every activity is individually classified, so every H% there sits on the same footing. The chip therefore reads plain “MODELED” without a qualifier. The qualified tokens above (Pattern-Reference Estimate, RACI-Grounded) matter when figures of different grounding appear side by side across domains. When other domains come into the sandbox, the chip takes the matching qualified token instead. The unit definition (U1) stays the same across all of them.

Open Items

Calibration of the anchor scale. Whether the six values should be calibrated, for example against a control-point rubric or against observed data, is an open item for Tim and GiGi. Changing them would shift every H% figure and point gap in the sandbox, and each change would be logged in the shared changelog (changelog-data.js).
