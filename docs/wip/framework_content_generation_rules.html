Formal, checkable rules — derived from GiGi's own site recommendations — meant to bind any future generator of framework content, human or AI-authored.

This catalog merges what were three separately-numbered documents — Visual System & Hierarchy, Navigation & Structure, and Language & Precision — into one continuously numbered list, currently Rule 1 through Rule 21 (Rule 2 retired, its number kept). Each still turns one of GiGi's site-recommendation groups (or, for Rules 19 and 20, a standard Tim set directly) into something checkable, not just a style preference, and each still names what it requires, what it applies to, and, where useful, points at a real page or decision already in the framework that shows the rule in action or in violation. What changes is only the numbering: under three separate "Rule 1…N" sequences, "Rule 3" meant something different depending on which document you were in. Under one catalog, "Rule 14" means exactly one thing everywhere it's cited — in this document, in the compliance audit, or in any future WIP proposal that references it. The three source documents are retained in the WIP folder for history but are superseded by this one.

One related distinction this catalog does not collapse: a rule is a checkable behavioral constraint on how content gets built ("every artifact draws its colors from the standing set"); a token is a specific value a rule governs (the hex code #1B4F8A). Rule 1 below is the rule; the token set it locks is a separate, referenced list, not eighteen more rules of its own. Tokens stay tokens — this catalog just makes sure "Rule N" never needs a second question ("which document's Rule N?") to answer.

Visual System & HierarchyRules 1–8
RULE 1Token Lock

Every framework artifact — HTML page, docx, or PDF — draws its colors exclusively from the standing token set, and every framework document also draws its fonts from it. Colors: navy #1B4F8A, navy-d #0D2D4F, navy-l #EEF3FA, gray #444, light gray #888, border #DDE3EE, amber #B8873F / amber-bg #FEF3C7 (reserved for draft/pending status only — never used decoratively), and light-blue #9FC2EE / #9FC0E8 (the nav-tagline and role-narrative banner accent). Status colors, used only to mean a state and never decoratively: green #166534 / #DCFCE7 (passed, agreed, created), red #991B1B / #FEE2E2 (flagged, deleted), orange #B45309 (redefinition recommended, updated), and slate #475569 (locked). Neutral UI colors: dark text #0D1B2A, label black #000000, draft-ribbon text #7A5A1E, masthead link #CFE0F5, page background #F4F6FB, row tint #FAFBFD, the grays #8A93A0 / #94A3B8 / #B8C0CC / #C8D0DC / #DCE1E8, the light fills #EDEFF3 / #F1F3F6, and the pill and tag accents #C7D8EE / #D6E8FF / #7A9CC6. Fonts (documents only): Georgia for headlines and serif emphasis, Segoe UI for body text, Consolas for labels, badges, and section numbers — genuine Microsoft Word-compatible fonts only, never Google Fonts or other web-only families, so a document renders identically whether it's opened as an HTML page, a Word document, or a PDF. Interactive UI — the sandbox and the dashboard — keeps its current type system (DM Sans, DM Mono, Playfair Display) and is not governed by the font clause. A generator does not introduce a new color, or a new font in a document, for a single artifact; a genuinely new visual need becomes its own proposal, not a local fix.

Applies to: Colors — every HTML page, docx build, or PDF the framework produces. Fonts — documents only: docx, PDF, and document-style HTML pages (WIP proposals, methodology and reference pages). Not interactive UI.

Already the de facto practice for colors across the dashboard, docs site, and every docx/PDF built to date — this rule just makes it binding rather than assumed. Corrected during the WIP compliance audit: the original list omitted the light-blue accent, which was already in universal, load-bearing use for nav taglines and role-narrative banners — now folded into the locked set instead of left as an unsanctioned extension. Status and neutral UI colors added Sept 24, 2026, after the Sandbox 7.0 sweep found them in deliberate, consistent use with no rule behind them; three near-identical row tints were consolidated into #FAFBFD at the same time. Font scope decided Sept 24, 2026 (Tim), after the same sweep: the Word-compatible font set governs documents only. The interactive UI keeps its current fonts, since it is never exported to Word and its type system is tuned for dense data tables.

RULE 2One Pattern Legend — Retired

Retired Sept 24, 2026. Tim and GiGi retired the five work patterns from all user-facing display, so there is no pattern legend left to govern. Every activity still carries its pattern in the data (GR-038), for possible future analytics only. The number stays reserved so existing citations remain correct. Original text, kept for the record: Anywhere the five HITL patterns (Decision, Knowledge, Document, Transaction, Exception) are referenced beyond a single passing mention, the content uses one fixed color-and-label mapping and either displays or links to the canonical pattern legend. A generator does not invent a new shorthand, abbreviation, or color for a pattern, and does not assume the reader already knows the mapping.

Applies to: Any page or document referencing pattern types — the dashboard, methodology page, maturity/RACI docs, any future role or readiness page.

Real gap today: patterns currently read "more like a legend than building blocks" (GiGi's own words) — no single reusable legend component exists yet.

RULE 3Extract the Load-Bearing Claim

Before finalizing any section of prose, the generator identifies that section's actual claim — a number, a finding, a governing statement — and renders it separately, in the standing pull-quote/callout treatment, rather than leaving it buried inside a paragraph.

Applies to: Any section built around a specific finding or number.

Reference case: the 18–20 point convergence gap belongs in a callout, the way the HAL 9000 line already does — today it still sits in a sentence.

RULE 4Callout Budget

No single page or document carries more than three callout or pull-quote boxes. If a draft produces more candidates than that, the generator ranks them by how load-bearing the underlying claim actually is and demotes the rest back to plain prose — it does not keep all of them.

Applies to: Every generated page or document, without exception.

A self-check worth running on our own recent work: an early draft of Talking Through Your Questions had four boxed callouts on one page before this rule existed.

RULE 5Standing Type Scale as Default

New documents start from the current, already-downsized type scale as their baseline — masthead H1 22–28px, H2 16–20px, body 13–14.5px, table header 11px, table body 12px, caption 12px — never a full-size print or Word default that then needs its own downsizing pass later. Major ideas get visible breathing room: each H2 section starts 36px below the content above it (27pt Space Before in Word), with 16px between paragraphs (12pt). No maximum paragraph width is set.

Applies to: Documents only — docx, PDF, and document-style HTML pages: the Readiness Table, Trust-dimension work, remaining domain RACI docs, People-side extension pages. Interactive UI (the sandbox and the dashboard) keeps its current sizes, which are tuned for dense data tables.

The August 5 downsizing pass across all 13 maturity docs and 7 RACI docs was this rule, applied reactively after the fact — the point is to stop needing that pass at all. Scoped to documents Sept 24, 2026 (Tim), after the Sandbox 7.0 sweep found the UI's smaller table sizes (10px headers, 12px body) are deliberate for dense data, not drift. Section spacing added the same day to cover the rest of GiGi's GR-004 ask for documents; the 36px H2 spacing is what the WIP document pages already use. Including the paragraph rule was considered but rejected. Implementing that in the UI would create a lot of white space and extra scrolling.

RULE 6Protect the Signature Line

Wherever the framework masthead appears, "Where human judgment belongs" is set on its own line, visually distinct in weight or color from the framework name beside it — never merged into the same sentence or run together with other boilerplate text.

Applies to: Every masthead: the live dashboard, the docs site, every WIP page.

RULE 7The Executive Layer Never Replaces the Technical Layer

Any simplified, executive-facing version of technical content — a briefing, a summary card, a pull-statement layer — links back to its full technical source. A generator may summarize; it may never publish a summary as a substitute with no path back to the underlying rigor.

Applies to: The CHRO-facing briefing series, and any future executive-summary layer built on top of existing technical pages.

This is the concrete, already-designed answer to GiGi's own Question 12 — not yet shown to her.

RULE 8Bottom-Align Column Headings

In any table, a column heading's text vertically aligns to the bottom of the header row, never the middle or top — so a short one-line label and a longer label that wraps to two lines still share the same baseline, and the header row reads as one clean line into the data below regardless of which columns wrap.

Applies to: Every table the framework builds — rule-gap and per-rule findings tables, per-document snapshots, composition/RACI/maturity tables, the WIP catalog.

Corrected during the WIP compliance audit: browsers and Word both default a table header cell to middle/top alignment, not bottom, so this was a real gap rather than an assumed default — fixed across every WIP HTML and docx table with a real column-heading row (the CHRO/HRBP Manager/Recruiter composition tables, From Concept to Principle's and The Shock Wave Effect's tables, and this audit's own tables) as this rule was written.

Navigation & StructureRules 9–11
RULE 9Problem-First Entry Points, Additive

Primary navigation offers at least one problem-framed entry point — "I am a CHRO — show me HR," "I am a CFO — show me Finance," "I am redesigning a role — show me Role Transition," "I want to understand AI readiness — show me Maturity" — alongside, never instead of, the existing structural/taxonomy navigation. A generator building a new landing surface includes a problem-first path into the content; it does not remove or bury the structural path to make room for it.

Applies to: The docs site's primary landing/navigation surface; any new top-level page.

Right now the site invites a visitor to "study the architecture" first — the fix adds a second door in, it doesn't replace the first one.

RULE 10One Canonical Explanatory Sequence

The five-step sequence — Technology Capability → Work Design → Human Judgment → Accountability → Readiness — is the framework's single canonical "explain it in a few seconds" statement. It appears verbatim, in this order, wherever the site attempts to summarize the whole framework in one line. A generator does not paraphrase, reorder, or invent a competing summary sequence.

Applies to: The site's homepage/landing hero, the About page, any executive briefing or summary card.

The same line already got the boxed step-flow treatment in the Talking Through Your Questions document — this rule makes that the one and only version, not a first draft of several.

RULE 11Hierarchy Fix, Not Redesign

Navigation and structure changes are evaluated first as hierarchy and information-architecture adjustments — reordering, re-labeling, re-emphasizing what already exists — tested against whether a first-time CHRO or CFO reader would know what to click. A full visual redesign, or a new page type built from a blank layout, is out of scope for a navigation fix and requires its own separate proposal.

Applies to: Any navigation or information-architecture change to the docs site or dashboard.

GiGi's own framing, kept as the rule's test: "the foundation is strong; the fix is hierarchy, not a redesign."

Language & PrecisionRules 12–18
RULE 12Protect the Proven Lines

"Where human judgment belongs" and "HITL as an organizational design standard, not a safety checkpoint" are locked language. A generator does not rewrite, replace, or paraphrase either line — under any editing pass, for any reason — without a separate, explicit change proposal reviewed on its own.

Applies to: Any page carrying these lines today, and any new page restating the framework's core identity.

RULE 13Name the Organizational Framing Explicitly

When introducing or summarizing the framework, content states plainly that this is an organizational design problem, not only a technology problem — language equivalent to "This is not only a technology problem. It is an organizational design problem." A generator does not let a technology-only framing stand uncorrected in introductory copy.

Applies to: Any About/overview/introductory section, and the opening of any new briefing.

RULE 14Modeled vs. Observed, Always Labeled

Any statistic or finding presented as evidence — the convergence gap, per-pattern deltas, any future readiness or trust metric — is explicitly labeled modeled/estimated or observed/validated at the point it's stated. A generator never lets a modeled figure read as an empirical fact by omission.

Applies to: Every numeric claim, in every doc, dashboard, and briefing.

The 18–20 point convergence gap is modeled, not observed — already true internally, it just needs that label attached everywhere the number appears, not only where it happens to be caveated today.

RULE 15No Absolute Claims About Safety or Control

A generator does not use absolute language — "structurally impossible," "nothing is a black box," or equivalents — about risk, safety, or control. It uses calibrated language instead: failure made harder to occur, easier to detect, easier to challenge and contain; decision ownership and escalation staying visible. Calibrated language is honest about residual risk; absolute language overclaims its absence.

Applies to: Any risk-, safety-, or governance-adjacent content.

RULE 16H% Carries Its Disclaimer

Any time H% or a human-involvement percentage is introduced or displayed, the content states — or links to a statement, reachable from the same view — that H% is not a headcount-reduction metric and should not be read as "X% fewer people." A generator does not present an H% figure in isolation without that context nearby.

Applies to: The dashboard, any RACI/maturity doc showing H%, any executive summary citing the convergence gap.

RULE 17"Designed," Not "Optimal," Unless Earned

A generator defaults to "designed" or "appropriate" rather than "optimal" when describing a maturity target or reference curve. "Optimal" is used only when a specific, justified claim is actually being made that the target is a universal standard — and that claim is stated outright, not implied by word choice alone.

Applies to: Any reference to M3 / Design Intent, or any future maturity target.

RULE 18Frame HAL as Origin Story, Not Operating Target

The HAL 9000 90/10 example is framed as describing how the framework was co-created — its origin story — never as a universal operating target for an adopting organization. Wherever the example appears, it carries language equivalent to "HAL was the warning. This framework is an attempt to build the answer," rather than presenting the 90/10 split as a prescriptive ratio.

Applies to: Any page or briefing using the HAL example.

WIP Proposal StructureRule 19
RULE 19One Shape for Every WIP Proposal

Every WIP catalog item that proposes a new concept, standard, or change to the framework follows the same five-section structure, in this order: Why This Now (what prompted this — a real trigger, not a manufactured one), The Problem (what's wrong with the current state, with a concrete example or mock-up where the proposal is visual), The Recommendation (the proposed fix, shown the same concrete way as the problem), Proposed Tokens (any new values the proposal introduces — colors, names, thresholds — outside the current locked set, noting whether they touch Rule 1 Token Lock or Rule 2 One Pattern Legend), and Build Note (what implementing this would actually require, once approved). A generator does not invent a different section order, rename a section, or add a sixth; a section with nothing real to say is dropped entirely rather than padded out.

Applies to: Any new WIP catalog item proposing a concept, standard, or change. Reference-only WIP items that propose nothing — GiGi's own review notes, the compliance audit — aren't proposals and don't need this shape.

Already the shape used by Work Pattern Color Standard, built the day before this rule existed; this rule makes that the standard for every proposal going forward rather than something incidental to that one. H% Provenance Badge predates this rule too and uses its own section names (Why This Now / The Real Distinction / Placement Decided / Naming Standard / Build Note) — a real, not-yet-closed gap, left as-is unless Tim wants it reshaped to match.

Category & Sequential PalettesRules 20–21
RULE 20WR Category Palette Lock

Anywhere the six Working-Relationship categories (Automation, Agent-delegation, Augmentation, Oversight, Judgment, Human-only) are referenced beyond a single passing mention, the content uses one fixed color-and-H% mapping and either displays or links to the canonical WR legend. The locked set: Automation #7DAEE0 (10%), Agent-delegation #5A8DC4 (28%), Augmentation #3D6FA8 (48%), Oversight #2457A3 (62%), Judgment #204474 (82%), Human-only #0D2D4F (95%, matching the Rule 1 navy-d token — deliberate, not coincidental). A generator does not invent a new color, shorthand, or H% for a WR category, and does not assume the reader already knows the mapping or the Progression Ceiling Rule it represents.

Applies to: Any page or document referencing WR / Progression Ceiling classifications — the Working Relationship Progression Table, the sandbox, Understanding Working-Relationship Progression, any future domain's WR rollout, and any dashboard or RACI view that adds a WR column.

Real gap closed by this rule (September 2026): the six-category palette was live across the WR table and sandbox with no accessibility validation and no locked source of truth. A colorblind-safety check (CIEDE2000, the same rigor Work Pattern Color Standard's own proposal used) found Oversight and Judgment sitting too close together at the dark end of the ramp — a real weakness, though not a colorblind-specific one, since the palette's single-hue design already makes it robust to red-green colorblindness on its own. Oversight (#29528A → #2457A3) and Judgment (#1E3F6E → #204474) were respaced; Automation, Agent-delegation, Augmentation, and Human-only were left untouched. Full validation and rationale in WR Category Palette Standard.

RULE 21Consequence-of-Error Palette Lock

Anywhere a Consequence-of-Error rating is shown, it uses one fixed color-and-weight mapping: Low #0072B2, Moderate #008460, High #9A6A00, Critical #C15500. Font weight rises with severity alongside color, so the tiers stay distinguishable without relying on color alone. A generator does not invent a new color for a consequence tier, does not reuse these four colors for anything else, and does not use red for a consequence tier.

Applies to: Any page or document showing Consequence-of-Error ratings — the sandbox’s activity cards, rollups, and checklists, and any future RACI, WR, or readiness view that adds the rating.

Set in Tim’s Sept 22, 2026 colorblindness review: derived from the Okabe-Ito palette (blue, teal, amber, burnt orange rather than green-to-red, so Low and Critical stay far apart under red-green colorblindness), darkened just enough to pass WCAG AA as text on white. The palette was live in the sandbox with no rule behind it until the Sandbox 7.0 sweep (Sept 24, 2026) found the gap.

Any future rule joins this catalog at Rule 22 and onward, whichever category it belongs to — the numbering never restarts, so a citation made today stays correct as the catalog grows.
