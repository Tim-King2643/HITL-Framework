Why 7.0 goes first

7.0 (HR) was the original domain build and is where the tagline drift, the Rule 1 Token Lock gap, and the unswept GR-002–GR-011 rules were all found. It's also the domain with the most history — which makes it the most likely place for other undetected drift, and the best test case for the new promotion policy (see the companion doc, Content Promotion Policy — Sandbox / WIP / Production) before rolling the same pass across 8.0 (IT) and 9.0 (Finance).

The goal of this pass is not a redesign. It's an audit-and-reconcile: confirm every page in 7.0 reflects the currently Adopted tokens and rules, fix what doesn't, and run every fix through the new ladder (Proposed → … → Adopted → Published) so the fix itself is the first real proof the policy works. Same shape as how 7.0, 8.0, and 9.0 were originally each built as complete, self-contained passes — this is that same seam, run backwards as a cleanup.

What gets fixed in this pass

Checked directly against the repo. Two of the three original concerns turn out to be smaller or larger than described:

  1. Tagline lock — confirmed already consistent. "Where human judgment belongs" appears identically in all 71 checked occurrences across live site, sandbox, and WIP. No fix needed here right now; this item can close, pending GiGi confirming she isn't seeing a different version somewhere I didn't check.
  2. Rule 1 Token Lock colors — confirmed, and larger than expected. Every 7.0 page checked (hitl_crud_pcf7_final.html, process_catalog_pcf7.html, rtp_chro.html, rtp_hr_generalist.html, and others) uses 15–40+ distinct hex colors against Rule 1's locked set of 8 (navy #1B4F8A, navy-d #0D2D4F, navy-l #EEF3FA, gray #444, light gray #888, border #DDE3EE, amber #B8873F/#FEF3C7). Some of this may be legitimate — status badges, semantic colors (red/green for pass/fail), or WR-category colors governed by Rule 12 rather than Rule 1 — but the gap is large enough that this pass needs to first separate "legitimately governed by a different rule" from "actually out of compliance" before proposing fixes.
  3. GR-002 through GR-011 — partially already swept. docs/wip/framework_content_generation_rules.html already maps each of these to a specific rule and status (e.g. GR-005 tagline → Rule 6 + Rule 12, Partially Addressed; GR-009 → Rule 17, Designed). The Requirements Register spreadsheet confirms the same statuses. What's still missing is the page-by-page confirmation — the rule-to-requirement mapping is designed, but no one has checked each 7.0 page against it yet.

A fourth item, not in the original three: resolve the duplicate HITL_Requirements_Register.xlsx (see inventory table above) — confirm which copy is authoritative and either delete the other or make clear one is a working copy that gets overwritten from the other.

Rebuild sequence

  1. Pull the real inventory. Get repo access (or Tim exports the 7.0 file list) and fill in the table above with actual paths, replacing the category placeholders.
  2. Confirm current rule text. Re-read Rule 1's Token Lock and GR-002–GR-011 as currently written — the check is only as good as knowing exactly what "correct" means.
  3. Audit page by page. For each 7.0 page: check tagline wording, check token/color compliance against Rule 1, check each of GR-002–GR-011. Record pass/fail per page, not just per rule.
  4. Draft fixes. For anything failing, draft the corrected content or code. Anything touching wording or a locked token goes into WIP as Proposed, not straight to a file edit — this is the first real run of the new ladder.
  5. Review and Adopt. Tim and GiGi review through Under Review → Concept Agreed → Text Approved → Adopted, same as any other WIP item.
  6. Publish. Tim commits the Adopted fixes. Each commit is verified live and logged in the production changelog, including every file touched — this is where the tagline's three-file spread gets caught for good.
  7. Close the loop. Update GR-002–GR-011's status from "not confirmed swept" to "swept as of <date>" with the audit results attached, so the next person doesn't have to redo this from scratch.

Explicitly out of scope

  • No visual redesign. This is a compliance and consistency pass against existing rules and tokens, not a new look for 7.0.
  • No new features or pages. Anything net-new belongs in its own WIP proposal, evaluated separately from this cleanup.
  • 8.0 and 9.0 content. Only touched if a shared partial (header/footer/nav) used by 7.0 is also used by them — in which case the fix and its changelog entry note every domain it affects, but the audit itself stays scoped to 7.0 pages.
  • Sandbox exploration. docs/sandbox/pcf7.html and similar stay sandbox; this pass checks that nothing leaked out of it unreviewed, but doesn't rework the sandbox itself.
  • Building the drift-check tooling mentioned in the promotion policy doc (an automated script that diffs a token across all files). Useful follow-on, but not a dependency for this pass, which can run manually.

After 7.0: 8.0 and 9.0

Once the 7.0 pass closes — tagline locked, Rule 1 confirmed, GR-002–GR-011 swept and logged — the same sequence repeats for 8.0 (IT) and then 9.0 (Finance), in the order they were originally built. Two things should be faster the second time:

  • The inventory shape (the table in "What a 7.0 rebuild touches") carries over directly — only the file paths change.
  • Any shared partials fixed during the 7.0 pass (header, footer, tagline, token source) are already correct for 8.0 and 9.0 if they truly are shared — the 8.0/9.0 passes just need to confirm that, not redo the fix.

Each domain still gets its own audit against its own domain-specific rules, but the promotion mechanics and the changelog habit should need no re-explaining by the third pass.

Rule 2 (One Pattern Legend) — confirmed, systemic violation

Two different color palettes exist for the same five HITL patterns, both in active use:

  • Dashboard canonical (hitl_dashboard_final.html's PATTERN_HEX): Decision #7B9FD1, Knowledge #A79AE0, Document #5EB8E0, Transaction #6FC48C, Exception #E88A8A
  • CRUD/RTP local scheme (defined as CSS variables on hitl_crud_pcf7_final.html and reused across all 5 rtp_*.html pages): Decision #1B4F8A/#EEF3FA, Knowledge #534AB7/#F3F0FE, Document #0369A1/#E0F2FE, Transaction #166534/#DCFCE7, Exception #991B1B/#FEE2E2

Worst case: hitl_crud_pcf7_final.html uses both in the same table row — the pattern-mix bar uses the dashboard-canonical color, and the pattern-name badge right next to it uses the local scheme's color, for the same pattern. Rule 2's own text already flags this as a known gap ("no single reusable legend component exists yet") — this confirms it's not just missing, it's actively inconsistent, and it's the dominant pattern across CRUD + all 5 RTP pages, not a one-off.

Rule 1 (Token Lock) — mostly clean on the literal set, but an unwritten extended palette

The 8 core tokens are used correctly everywhere. But a second, consistent set of UI colors appears on every single page checked and isn't written into Rule 1 at all: dark text #0D1B2A, body background #F4F6FB, masthead accent #6E8CB8, table-header tint #CFE0F5, card background #FAFBFD, plus the semantic status pair green #166534/#DCFCE7 and red #991B1B/#FEE2E2 (used consistently for status states like Implemented/Open across pages). This is the same shape of gap Rule 1's own history note already describes for the light-blue accent — de facto universal use, never folded into the locked list. Recommend folding these into Rule 1 as a second proposal, rather than treating every page as non-compliant for using them.

Recommendation

Two separate WIP proposals, not one:

  1. Fix Rule 2 compliance — pick one pattern palette (the dashboard's, since it's the one Rule 2's own text points to) and update all 6 affected pages (CRUD + 5 RTP pages) to use it consistently, including fixing the CRUD page's same-row conflict.
  2. Extend Rule 1's locked set — formally add the UI/status colors found universally in use (dark text, body bg, masthead accent, table tint, card bg, status green/red) so the rule actually describes current practice, the same way the light-blue accent was folded in previously.

The sandbox page is excluded from both — it's explicitly out of promotion scope per this doc's earlier section.

Work Pattern → Working Relationship display migration (scoped 2026-09-21)

Tim and GiGi have agreed to a bigger change than reconciling the two pattern-color palettes above: the five work patterns (Decision, Knowledge, Document, Transaction, Exception) stop being shown to site visitors at all. They stay in the backend/data layer for possible future analytics, and the six Working-Relationship categories (Automation, Agent-delegation, Augmentation, Oversight, Judgment, Human-only) become the primary, actionable, user-facing lens instead. In GiGi's words, relayed by Tim: "The working relationship is the thing that gives us something actionable... I do not think the end user needs to see both."

This supersedes the standalone colorblind-safety fix framed earlier in this doc — a new pattern palette isn't needed if patterns aren't displayed at all.

Page inventory — where the badge markup actually lives

Counted directly against the live repo export by grepping for the rendered badge/card markup itself (.pat-badge, .capmap), not just the pattern words appearing in prose:

  • Role Transition Profiles (rtp_*.html, 25 pages) — show pattern badges and already show Working Relationship cards correctly. Lowest-effort group: badge removal only.
  • CRUD Tables (hitl_crud_pcf7/8/9_final.html, 3 pages) — pattern badges, no Working Relationship display yet. Needs badge removal + a Working Relationship column/chip added.
  • RACI Tables (hitl_raci_pcf7/8/9_final.html, 3 pages) — same as CRUD.
  • Maturity Tables (hitl_maturity_pcf8/9_final.html, 2 pages) — same as CRUD. (hitl_maturity_scale.html is narrative only, no badge markup, no change needed.)
  • Value Stream Profiles (vsp_*.html, 18 pages) — already clean: Working Relationship only, via inline-styled .capmap-card elements using Rule 20's locked palette. This is the pattern the other groups get brought up to.
  • Dashboard (hitl_dashboard_final.html) — shows an aggregate pattern-mix bar (not per-activity badges) alongside Working Relationship. Flagged as a separate decision — arguably the legitimate backend/analytics use GiGi described, not a per-item label.

33 pages total need a pattern badge removed; 8 of those (CRUD/RACI/Maturity) also need Working Relationship added.

Decisions (Tim)

  • Rule 5 gains section spacing for documents: 36px above each H2 (27pt in Word), 16px between paragraphs (12pt). Including the paragraph rule was considered but rejected; implementing that in the UI would create a lot of white space and extra scrolling.
  • Rule 2 (One Pattern Legend) retired, its number kept so citations stay correct.
  • Rule 21 (Consequence-of-Error Palette Lock) added.
  • GR-003 closed, using a new Closed status in the register.
  • GR-006, GR-007, and GR-011 keep their current status and will reach the sandbox through the development methodology.
