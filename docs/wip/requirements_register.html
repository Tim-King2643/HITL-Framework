Standard Design Spec Template — the section shape every design-spec document should follow
SectionPurposeContent Contract
Title BlockIdentify the doc and its authority.Framework name/tagline; document title; one-line subtitle naming the doc type (e.g. “A Design Methodology”); author line (names · date · doc status); a status callout box stating stage (concept/draft/adopted), what it replaces or extends, current validation status, and what it explicitly does NOT substitute for.
1. Why This Layer ExistsJustify the work before describing it.The concrete problem or evidence that broke the prior model — real examples, not hypotheticals. State plainly what the new layer measures that the old one didn’t.
2. Core Model / ConceptDefine the central construct precisely.The new classification, category set, or construct being introduced, defined in terms a reader can apply consistently — not just named.
3. Data ModelSpecify what replaces or extends the prior data.The concrete fields/structure, with a plain mapping from old → new (e.g. “replacing M1–M5 with Current State and Progression Ceiling”).
4. GranularityState where each kind of data lives, and why.Per-activity vs. per-role vs. per-org, with the reasoning for each choice, not just an assertion.
5. Gate / Decision Logic (if applicable)Define what has to be true before something is allowed to happen.Every independent signal/axis involved, what each one measures, its granularity, and its instrument — explicitly marked “existing” or “new, no instrument yet” for each one.
6. Evidence / Instrumentation per ComponentMake honesty about data-readiness structural, not a caveat.For every sub-part that isn’t fully instrumented yet: what evidence would be needed, at what volume/threshold to be trusted, and where that evidence would actually come from.
7. Downstream / Propagation EffectsShow how the change ripples outward.How this layer’s output feeds the next layer up (e.g. activity → role → manager → team → org), using one consistent question set.
8. Pilots / ValidationProve the model against real data, not synthetic data.At least one real walkthrough against real classified data, spanning different conditions — including findings that complicate or partially break the model.
9. Known Open ConstructsKeep the honesty ethos structural.Every concept identified as relevant but not yet instrumented, named plainly, with one sentence on why it’s hard and what it’s not the same as.
10. Sourcing, Validation & Scope BoundaryMake provenance and boundaries explicit.Where the source data/ground truth comes from; what’s deliberately left out as a separate parallel track; what this doc does not claim to resolve.
ClosingAttribute the work.Copyright/attribution line matching the rest of the framework’s documents.
