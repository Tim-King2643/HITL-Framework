Working Relationship as the Primary Display Lens

Retire the five work-pattern labels and colors from every user-facing page; keep them in the backend for future analytics; make the six Working-Relationship categories the thing people actually see
Documentation Dashboard Work in Progress
Concept stage — not yet part of the framework. This proposal supersedes the in-progress Work Pattern Color Standard concept: that proposal fixed the pattern palette's colorblind-accessibility problem, but if patterns stop being displayed to users at all, the problem it was solving no longer needs a display-layer fix. Recommend marking that item Superseded rather than continuing to review it — see "What happens to the old proposal" below.
"The biggest shift for me is that the working relationship now feels like the most concrete place to start. It tells us, at the activity level, what the human and AI are actually doing together. That is much easier to understand and much easier to test than asking the pattern label to carry the whole story. I would keep the original patterns in the backend because they may still matter analytically or technically, but I do not think the end user needs to see both. The working relationship is the thing that gives us something actionable: Automation, Agent-delegation, Augmentation, Oversight, Judgment, or Human-only."GiGi Garcia, relayed by Tim King, 2026-09-21

Why This Now

Tim and GiGi have agreed: the five work patterns (Decision, Knowledge, Document, Transaction, Exception) stop being something a site visitor sees, and the six Working-Relationship categories (Automation, Agent-delegation, Augmentation, Oversight, Judgment, Human-only) become the primary lens instead. Patterns describe what kind of work an activity is; Working Relationship describes what the human and the AI are actually doing together on it — and it's the second question a reader actually came to the site to answer. Patterns aren't being deleted. They stay in the backend/data layer, available if pattern-level analytics turn out to matter later — they just stop competing with Working Relationship for the reader's attention on every page.

The Problem

Right now the two classifications are shown side by side in some places and not at all in others, with no single page consistently leading on Working Relationship. The Recommendation

Two moves, applied consistently across the 33 pages that currently show a pattern badge (CRUD ×3, RACI ×3, Maturity ×2, RTP ×25):

1. Remove the pattern badge from the rendered page. The pattern value itself isn't deleted — it stays wherever it's already stored in each page's data (the same PATTERN_META/local pattern-object source the badges currently read from), just no longer rendered as a visible chip. That satisfies "keep it in the backend for possible future analytic use" without a data migration — only the display templates change.

2. Where Working Relationship isn't shown yet, add it — using the design already proven on the Value Stream Profile pages and the RTP pages. Those pages already render Working Relationship with Rule 20's locked palette via inline-styled .capmap-card elements (name, one-line description, activity count, H% ceiling value). CRUD, RACI, and Maturity tables need a per-row Working Relationship chip or column added using the same six locked colors — no new visual design work, just extending an existing, already-governed pattern to three more page types.

What happens to the old proposal

Recommend marking Work Pattern Color Standard Superseded rather than Denied — its colorblind-safety finding (Transaction/Exception nearly indistinguishable under deuteranopia; Decision/Knowledge too close under normal vision) is still true and still worth having on record. It just no longer needs to become a live display change, since the pattern colors it was fixing won't be displayed. If patterns are ever surfaced again for analytics tooling aimed at Tim or GiGi rather than end users, that validated palette is sitting there ready to reuse — recommend leaving a note to that effect on the superseded proposal rather than deleting it.

Proposed Tokens

None new. This proposal is entirely built on Rule 20's already-locked Working-Relationship palette — the same six hex values already live on every Value Stream Profile page. No token lock change needed for the six colors themselves; the only governance action is extending where they're used.

Build Note

Recommended sequence, easiest and lowest-risk first:

1. RTP pages (25 files) — delete-only. Each page already renders its Working Relationship card set correctly; this step is just removing the .pat-badge markup and its legend, nothing to build.

2. CRUD / RACI / Maturity tables (8 files) — the real build. Same badge removal, plus adding a Working Relationship column/chip per row, styled from the same locked palette and card pattern already proven on the VSP and RTP pages. Recommend building the pattern once against one CRUD page, confirming it reads correctly, then repeating across the other seven.

3. Dashboard — hold for a separate decision. Its pattern-mix bars are aggregate, not per-activity, and may be the legitimate backend/analytics use case GiGi flagged rather than something this proposal needs to touch.

Underlying pattern data (the PATTERN_META/pattern-object values each page currently reads its badge from) is left in place throughout — nothing in this build touches the data layer, only what's rendered from it.
