Working Relationship as the Primary Display Lens

Retire the five work-pattern labels and colors from every user-facing page; keep them in the backend for future analytics; make the six Working-Relationship categories the thing people actually see
Documentation Dashboard Work in Progress
Concept stage — not yet part of the framework. This proposal supersedes the in-progress Work Pattern Color Standard concept — see "What happens to the old proposal" below.
"The biggest shift for me is that the working relationship now feels like the most concrete place to start. It tells us, at the activity level, what the human and AI are actually doing together. That is much easier to understand and much easier to test than asking the pattern label to carry the whole story. I would keep the original patterns in the backend because they may still matter analytically or technically, but I do not think the end user needs to see both. The working relationship is the thing that gives us something actionable: Automation, Agent-delegation, Augmentation, Oversight, Judgment, or Human-only."GiGi Garcia, relayed by Tim King, 2026-09-21
Related Requirements — Requirements Register
  • GR-003 — give the work classification a stronger, consistent visual identity site-wide (Reframed — Working Relationship, not pattern, is now the identity that needs it)

Why This Now

Tim and GiGi have agreed: the five work patterns (Decision, Knowledge, Document, Transaction, Exception) and their %-based maturity scores stop being something a site visitor sees. They weren't actionable — they described what kind of work an activity was, not what's actually changing about it. The six Working-Relationship categories are actionable: they show current state, how far an activity can go, and the path between. Patterns aren't deleted, just no longer the thing rendered on the page — they stay in the data layer for future backend analytics. The mockup below shows the shift on one real activity.

The Recommendation

1. Remove the pattern badge from the rendered page. The value itself stays wherever it's already stored (the same PATTERN_META/pattern-object source the badges read from) — only the display templates change.

2. Where Working Relationship isn't shown yet, add it as the progression ramp — Current State → Progression Ceiling across all six categories, reached steps marked, the ceiling locked, each step clickable. It carries the same locked Rule 20 colors as the VSP/RTP cards, but says more than a single label can, as shown above. CRUD, RACI, and Maturity tables get this ramp per row; no new visual design work, since it's already built and proven in the sandbox.

What happens to the old proposal

Recommend marking Work Pattern Color Standard Superseded rather than Denied — its colorblind-safety finding is still true and still worth having on record, it just no longer needs to become a live display change, since the pattern colors it was fixing won't be displayed to users.

Build Note

Scoped to completing the PCF 7.0 (HR) implementation first; 8.0/9.0 get the same treatment in a later pass once this one is proven out. Recommended sequence, easiest and lowest-risk first:

1. PCF 7.0 RTP pages (rtp_7*.html) — delete-only. Each page already renders its Working Relationship card set correctly; this step is just removing the .pat-badge markup and its legend, nothing to build.

2. hitl_crud_pcf7_final.html and hitl_raci_pcf7_final.html — the real build. Remove the pattern badge, add the sandbox's progression-ramp graphic per row (Current State → Progression Ceiling across the six locked categories, as mocked up above), reusing its existing markup/styling rather than a new circle or chip design. Table rows will need to accommodate a full-width strip rather than squeeze the ramp into an existing narrow column. Build against the CRUD page first, confirm it reads correctly, then repeat on RACI. (PCF 7.0 has no maturity table to update.)

3. Dashboard and PCF 8.0/9.0 — out of scope here. The dashboard's pattern-mix bars are aggregate, not per-activity, and may be the legitimate backend/analytics use case GiGi flagged; 8.0/9.0's CRUD/RACI/Maturity tables get the same two-step treatment once the 7.0 build is confirmed working.

Underlying pattern data (the PATTERN_META/pattern-object values each page currently reads its badge from) is left in place throughout — nothing in this build touches the data layer, only what's rendered from it.
