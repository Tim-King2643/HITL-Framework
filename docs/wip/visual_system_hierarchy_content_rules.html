Framework Content Generation Rules

Visual System & Hierarchy
Formal, checkable rules — derived from GiGi's own site recommendations — meant to bind any future generator of framework content, human or AI-authored.
Documentation Dashboard Work in Progress
Concept stage — not yet part of the framework. Per the Concept → Feasibility Review → Approved lifecycle established in From Concept to Principle, this is Claude's feasibility pass only. Nothing here binds any actual content generation until both Tim and GiGi approve it.

These seven rules turn the six "Visual system & hierarchy" recommendations from GiGi's review notes into something checkable — not just a style preference, but a set of constraints a content generator (Claude, building a new page or document) can actually be held to. Each rule names what it requires, what it applies to, and, where useful, points at a real page or decision already in the framework that shows the rule in action or in violation.

RULE 1Token Lock

Every framework artifact — HTML page, docx, or PDF — draws its colors and fonts exclusively from the standing token set. Colors: navy #1B4F8A, navy-d #0D2D4F, navy-l #EEF3FA, gray #444, light gray #888, border #DDE3EE, and amber #B8873F / amber-bg #FEF3C7 (reserved for draft/pending status only — never used decoratively). Fonts: Playfair Display for headlines and serif emphasis, DM Sans for body and UI text, DM Mono for labels, badges, and section numbers. A generator does not introduce a new color or font for a single artifact; a genuinely new visual need becomes its own proposal, not a local fix.

Applies to: Every new HTML page, docx build, or PDF the framework produces.

Already the de facto practice across the dashboard, docs site, and every docx/PDF built to date — this rule just makes it binding rather than assumed.

RULE 2One Pattern Legend

Anywhere the five HITL patterns (Decision, Knowledge, Document, Transaction, Exception) are referenced beyond a single passing mention, the content uses one fixed color-and-label mapping and either displays or links to the canonical pattern legend. A generator does not invent a new shorthand, abbreviation, or color for a pattern, and does not assume the reader already knows the mapping.

Applies to: Any page or document referencing pattern types — the dashboard, methodology page, maturity/RACI docs, any future role or readiness page.

Real gap today: patterns currently read "more like a legend than building blocks" (GiGi's own words) — no single reusable legend component exists yet.

RULE 3Extract the Load-Bearing Claim

Before finalizing any section of prose, the generator identifies that section's actual claim — a number, a finding, a governing statement — and renders it separately, in the standing pull-quote/callout treatment, rather than leaving it buried inside a paragraph.

Applies to: Any section built around a specific finding or number.

Reference case: the 18–20 point convergence gap belongs in a callout, the way the HAL 9000 line already does — today it still sits in a sentence.

RULE 4Callout Budget

No single page or document carries more than three callout or pull-quote boxes. If a draft produces more candidates than that, the generator ranks them by how load-bearing the underlying claim actually is and demotes the rest back to plain prose — it does not keep all of them.

Applies to: Every generated page or document, without exception.

A self-check worth running on our own recent work: an early draft of Talking Through Your Questions had four boxed callouts on one page before this rule existed.

RULE 5Standing Type Scale as Default

New content starts from the current, already-downsized type scale as its baseline — masthead H1 22–28px, H2 16–20px, body 13–14.5px, table header 11px, table body 12px, caption 12px — never a full-size print or Word default that then needs its own downsizing pass later.

Applies to: Any new document type: the Readiness Table, Trust-dimension work, remaining domain RACI docs, People-side extension pages.

The August 5 downsizing pass across all 13 maturity docs and 7 RACI docs was this rule, applied reactively after the fact — the point is to stop needing that pass at all.

RULE 6Protect the Signature Line

Wherever the framework masthead appears, "Where human judgment belongs" is set on its own line, visually distinct in weight or color from the framework name beside it — never merged into the same sentence or run together with other boilerplate text.

Applies to: Every masthead: the live dashboard, the docs site, every WIP page.

RULE 7The Executive Layer Never Replaces the Technical Layer

Any simplified, executive-facing version of technical content — a briefing, a summary card, a pull-statement layer — links back to its full technical source. A generator may summarize; it may never publish a summary as a substitute with no path back to the underlying rigor.

Applies to: The CHRO-facing briefing series, and any future executive-summary layer built on top of existing technical pages.

This is the concrete, already-designed answer to GiGi's own Question 12 — not yet shown to her.

If these seven are approved, the same treatment — specific, checkable rules rather than general advice — would follow for Navigation & Structure and Language & Precision next, completing the set drawn from GiGi's full site-recommendations summary.
