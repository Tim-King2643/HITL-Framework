1. Why This Layer Exists

The framework describes no specific organization, so it cannot know how any activity is done today. Its Current State values were modeled judgments of typical practice, shown as if they were readings.

The same question had already come up for systems of record, which were changed from vendors to generic categories on Sept 26 (CL-008). Applied to Current State, it leads somewhere bigger. Tim’s answer:

“I would like to design the framework for exactly that purpose. To have an organization assessment layer. That would enable the framework to become a real working reference model that guides organizational assessments and AI design intent. I would initialize our current reference to the Human-only stage. The ceiling is our reference point for what needs to stay human by design.”

What the framework can say generically is what is true of the work itself: its consequence of error, the legal, relational and accountability limits on it, and so how far AI may take it. That is the Progression Ceiling. Where a particular organization stands today is a fact about that organization, and belongs to its assessment.

4. Granularity

  • Activity level for every assessment, because the ceiling and consequence live there.
  • Process and role level computed from activities, the same way the People View rolls up today, with coverage stated (“23 of 118 activities assessed”).
  • Organization level for the whole picture: design space remaining, activities beyond design intent, and verification load across roles.

5. Decision Logic

Resolution rule. For each activity: Current State is the organization’s assessed value where one exists, otherwise the Human-only baseline. The effective ceiling is the reference ceiling, or the organization’s governance ceiling where it is lower.

Ceilings can be lowered, not quietly raised. An organization may hold an activity lower as a governance choice. Setting it higher than the reference ceiling requires a recorded reason, and the activity stays flagged as a divergence from the reference model.

6. Instrumentation and Build Work

A. Enabling work

  1. Reset the reference Current State to Human-only for all 118 activities, logging the modeled values being retired.
  2. Review the ceilings as design intent with GiGi, since they now carry the framework’s central claim. 42 activities have a ceiling at Automation, meaning nothing in them has to stay human.
  3. Organization data model and storage: the record shapes in section 3, stored privately behind the Worker; ABC Test Org in the repo.
  4. Resolution logic: the rule in section 5, used by every view and computed figure.
  5. Assessment method: how an activity is placed on the ramp and what evidence counts, building on the evidence ladder (GR-037) and GiGi’s workforce validation check (GR-022). Built into the template in section 8a and revised through its pressure test.
  6. Access per organization: an organization’s data visible only to those it names.

B. UI work

  1. View selector: Reference baseline, Reference design intent, or a named organization.
  2. Source chips: REFERENCE for reference values, ASSESSED (with date and assessor) for an organization’s.
  3. Coverage on every rollup.
  4. Beyond-design-intent flag on any activity assessed past its ceiling.
  5. Gap view: an organization against design intent, activity by activity and role by role.
  6. Interactive activity assessment template: a guided page that walks each activity to a working relationship, records the evidence, and flags anything past design intent (section 8a).

7. Downstream Effects

  • The Working-Relationship view reads as Human-only to ceiling in the reference, with an organization’s assessed state placed between.
  • Work product and the Shock Wave: verification load becomes an organization finding, with a design-intent version for the reference.
  • Documentation (GR-048) describes Current State as an organization’s assessed value, and the ceiling as design intent.
  • How the framework can be offered: the reference model as a product in its own right, assessments against it as engagements, and, with each organization’s consent, comparisons across assessed organizations. Commercial terms are for Tim and GiGi to settle separately, per their Co-Development Principles.

8. Prototype and Pilot

Prototype with a test organization. Components cannot be designed or tested without organization data, so the layer is built against ABC Test Org: a test organization defaulted to the reference, with every activity at Human-only and every ceiling the reference ceiling. Its Current State is then set through the interactive assessment template, working-relationship assessment first, with other areas (governance ceilings, role mapping, CRUD) added as we determine.

Rules for test data. ABC Test Org carries a TEST chip on every value and a banner whenever it is selected; it is excluded from any benchmark or cross-organization comparison and is never cited as a finding. Because it is not confidential it can live in the repo, under the changelog check; real organizations never do.

Pressure test. Tim and GiGi assess ABC through the template, starting with the HRBP Manager’s 23 activities, and record where the questions, definitions or evidence prompts fail: ambiguous answers, boundary cases between categories, and time taken per activity. The template and the process are revised from that before any real organization is assessed.

8a. The Interactive Activity Assessment Template

For each activity the template shows what the reference model knows (process, activity, Accountable and Responsible roles, Consequence of Error, and the ceiling with its factors), then asks a short sequence of questions drawn from the locked category definitions:

  1. Does AI play any part in this activity’s work? No → Human-only.
  2. Does AI only supply inputs (data, rankings, benchmarks) for a person’s own reasoning? Yes → Judgment.
  3. Does a person remain the primary actor, with AI assisting in real time and no separate approval step? Yes → Augmentation.
  4. AI produces the complete work: does a person review and approve every instance before it takes effect? Yes → Oversight.
  5. Does a person handle only the exceptions the AI flags? Yes → Agent-delegation. No person in the loop, exceptions included → Automation.

The answers propose a working relationship, which the assessor confirms or overrides with a reason. The template then records the evidence type (observed practice, system configuration, interview, document), who gave it, a confidence level and a note, and flags the activity if the result is past its ceiling. Progress shows by process and by role.

9. Known Open Constructs

Default reference view

Whether the sandbox opens on the baseline, the design intent, or both side by side.

Ceilings under review

Whether the 42 Automation ceilings, and the rest, hold up as design intent before the reset is published.

Raising a ceiling

What reason is sufficient for an organization to go past the reference ceiling, and how it is reviewed.

Organization roles

Real organizations have their own roles. Mapping them to the reference role taxonomy is needed before role-level findings mean anything.

Reference versions

When a ceiling changes after an organization is assessed, which version its findings are read against.

Evidence standard and confidentiality

What evidence an assessment requires, and how organization data is protected and, if ever, aggregated.

10. Sourcing, Validation & Scope Boundary

Source is Tim’s design decision of Sept 26, 2026 and Sandbox 7.0’s current data (118 classified activities; ceilings: 28 Judgment, 5 Oversight, 8 Augmentation, 35 Agent-delegation, 42 Automation). Scope is PCF 7.0 in the sandbox; the design is domain-neutral so every domain can use it. Production is out of scope until the full production rebuild.
