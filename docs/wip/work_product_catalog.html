Master data — read live from Sandbox 7.0

Since Sept 26, 2026 the catalog lives in the sandbox as master data (WORK_PRODUCTS, CL-007), and this page reads it, and the CRUD that names each work product, every time it opens, so it cannot drift. Changes are made in the sandbox first and logged in the changelog. Every entry is still Draft until Tim and GiGi confirm the definitions; the page keeps its vote for that.

Related Requirements — Requirements Register

1. What Each Entry Holds

The catalog stores six fields per work product. Who produces it and who reads it are not stored here; they come from the CRUD links, so they can never disagree with them.

FieldRule
IDWP-domain-sequence, such as WP-7-12. Permanent: a retired ID is never reused. New work products take the next number (WP-7-38 and WP-7-39 were added Sept 26).
NameThe work product as people in the role would name it, without the system.
DefinitionOne line saying what it is.
System of recordThe kind of system that holds the authoritative copy, named as a generic category (for example, Applicant Tracking System), never a vendor: the framework describes no specific organization.
StatusDraft, Active or Retired. Retired entries stay in the catalog so changelog history and old links still resolve.
Model outputYes when the work product is itself the output of an AI or statistical model. It then counts as AI-touched for everyone downstream, whatever its producing activity's working relationship.

3. Review Decisions — Tim, Sept 25, 2026

Q1 — One system of record: iCIMS

Job Posting and Offer Letter now name iCIMS alone. LinkedIn Recruiter is where postings are distributed and DocuSign is where offers are signed; neither holds the record.

Q2 — Merged into Applicant Record and HR Analytics Report

Candidate Profile is merged into Applicant Record, and HR Report into HR Analytics Report (system of record Visier). Applicant Record's creator is 7.2.5, whose activity 7.2.5.2 is “Create applicant record”; 7.2.2 (which maintains the candidate pool), 7.2.3 and 7.2.4 update it. 7.7.1 Manage reporting processes now updates HR Analytics Report instead of creating a separate report.

Q3 — One creator each, from the activities

Payroll Record: 7.5.4 Administer Payroll creates it. 7.5.1 now updates it, through activity 7.5.1.5 “Administer compensation and rewards to employees,” which feeds reward payouts into payroll. HR Analytics Report: 7.7.8 creates it, through 7.7.8.2 “Develop insights” and 7.7.8.3 “Communicate workforce analysis outcomes.” None of 7.7.7's five activities produces a report (they set requirements, questions, method and data sources), so 7.7.7 no longer creates it and keeps only its read of the Employee Master Record. No work product now has more than one creating process.

Sept 26 — Requisition Record created in 7.2.1

Tim, reviewing the activity-level draft: the requisition is opened in 7.2.1.2 Open job requisitions, so 7.2.1 creates the Requisition Record and 7.1.2 no longer does. None of 7.1.2’s sixteen activities opens a requisition. Logged as CL-006. The ID stays WP-7-02.

Q4 — Renamed

“T&A Record” is now “Time and Attendance Record” everywhere in the sandbox.

Q5 — Model outputs flagged

Added the Model output field. The Retention Risk Score is marked Yes: it is AI-touched by nature, whatever its producing activity's working relationship.

3a. Decisions from the Activity-Level Review — Tim, Sept 26, 2026

Two new work products

Outputs found while reasoning each activity are added to the catalog when identified. WP-7-38 Staffing Plan is created in 7.2.1.1; WP-7-39 Performance Program is updated in 7.3.2.4, and its creator is not identified yet.

Systems named generically

Every system of record is now a generic category rather than a vendor, since the framework is not based on a specific organization (CL-008). The Sept 25 decisions above name the vendors that were in the data at the time; iCIMS is now the Applicant Tracking System and Visier the People Analytics Platform.

CRUD reasoned per activity, process CRUD derived

For the HRBP Manager’s 11 processes, each activity’s links are reasoned from the activity and the process CRUD is derived from them (CL-007). That dropped 7.6.2’s update of the ER Case Record, which no activity supports, made offboarding the Separation Record’s creator with retirement updating it, and added ten links the process CRUD never had. See Activity-Level CRUD — HRBP Manager.

4. What the Catalog Shows

The read side is still thin. The count of work products with no recorded reader is shown above, live. It falls as each role’s activities are done, because reasoning from the activity finds reads the process CRUD never captured.

Unconfirmed process CRUD is inferred, not recorded. Activity-level links carry the date Tim confirmed them. Stored process-level CRUD has no such flag: fifteen processes’ entries are written in a slightly different format from the other 22, matching the sandbox’s own count of unconfirmed ones, and the dashed codes are that inference. The gap closes as each process moves to activity-level CRUD.

5. Next Step

Tim and GiGi confirm the definitions, and each entry moves from Draft to Active. The add, change and retire functions for the catalog (GR-050) are still to be designed; until then, changes are hand-edited in the sandbox and caught by the changelog check.
