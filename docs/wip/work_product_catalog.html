Work-Product Catalog — Sandbox 7.0

The 39 work products in PCF 7.0, each with a permanent ID, a definition and a system of record
Documentation Dashboard Work in Progress
Draft for review — item A1 of the Work Product spec

Every name and system of record comes from the process-level CRUD entries in Sandbox 7.0. The definitions are Claude's first pass, for Tim and GiGi to correct. Once approved, the catalog becomes master data in the sandbox, the first new entity under GR-050, and activity-level CRUD (A2) links to these IDs instead of free text.

1. What Each Entry Holds

The catalog stores five fields per work product. Who produces it and who reads it are not stored here; they come from the CRUD links, so they can never disagree with them.

FieldRule
IDWP-domain-sequence, such as WP-7-12. Permanent: a retired ID is never reused.
NameThe work product as people in the role would name it, without the system.
DefinitionOne line saying what it is.
System of recordThe one system that holds the authoritative copy. The vendors are Sandbox 7.0's illustrative examples.
StatusDraft, Active or Retired. Retired entries stay in the catalog so changelog history and old links still resolve. Every entry below is Draft.

3. Questions for Review

Q1 — One system of record

Job Posting (iCIMS / LinkedIn Recruiter) and Offer Letter (iCIMS / DocuSign) name two systems. Proposed: iCIMS holds both; LinkedIn is where the posting is distributed and DocuSign is where the offer is signed.

Q2 — Possible duplicates

Applicant Record and Candidate Profile both live in iCIMS, created by different processes (7.2.5 and 7.2.2). HR Report (Workday Prism) and HR Analytics Report (Visier) may overlap too. Keep each pair as two work products, or merge?

Q3 — Two creating processes

Payroll Record is created in both 7.5.1 (rewards) and 7.5.4 (payroll); HR Analytics Report in both 7.7.7 (develop) and 7.7.8 (implement). Most likely one creates it and the other updates or reads it. Settling this matters because production mode follows the producer.

Q4 — Spell out the name

Proposed: rename “T&A Record” to “Time and Attendance Record.”

Q5 — Model outputs as work products

Retention Risk Score is itself a modeled estimate, and no process reads it. Should it carry a flag marking it as an AI output by nature, whatever its producing activity's working relationship?

4. What the Draft Surfaced

The read side is thin. 26 of the 39 work products have no process recorded as reading them, including Candidate Profile, Survey Response and Retention Risk Score. Some are genuinely end points; most are probably reads the CRUD entries never captured. Verification load counts only reads, so today's figures in the Work Product spec undercount. Filling in reads belongs with activity-level CRUD (A2).

Which 15 processes are unconfirmed is not recorded in the data. The sandbox says 22 of 37 processes have confirmed CRUD but carries no flag saying which. Fifteen entries are written in a slightly different format from the other 22, which matches the count, so the dashed codes above are an inference, not a record. Proposed: add a confirmed flag to each CRUD link when A2 moves CRUD to the activity.

5. Next Step

Once Tim and GiGi settle the definitions and the five questions, the catalog moves into Sandbox 7.0 as master data through the master-data lane, with a changelog entry and the changelog check extended to cover it (GR-050). Activity-level CRUD (A2) then links each create, read, update and delete to these IDs.
