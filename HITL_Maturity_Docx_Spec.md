# HITL Maturity Assessment (docx/pdf) — Locked Design Spec

**Status:** Approved by Tim King, August 8, 2026; updated same day through the header-caps/vertical-alignment round. This is the canonical spec for `hitl_maturity_<slug>_final.docx` across every PCF domain. Generated by the domain-parameter-driven script `gen_maturity.js`, invoked as:

```
node gen_maturity.js <path-to-domain-json> <output-slug>
# e.g. node gen_maturity.js pcf7_full.json pcf7
#      node gen_maturity.js pcf8_full.json pcf8
```

The script takes the domain's extracted JSON (code, name, l1mv, groups[].l3[].l4[]) and produces `hitl_maturity_<slug>_final.docx`. All values below are pulled directly from the approved generator source — this file **is** the spec; if the generator ever changes, update this file to match, not the other way around.

This doc type shares its structural/visual conventions with **`hitl_raci_<slug>_final.docx`** (see the companion file `HITL_RACI_Docx_Spec.md`) — both are generated by sibling domain-parameterized scripts and should stay in sync on anything not specific to Maturity's M1–M5 columns or RACI's R/A/C/I columns.

### Header row
Fill `1B4F8A` (NAVY), text `FFFFFF`, bold, size 11, **ALL CAPS** (via docx's `caps: true` TextRun property — renders uppercase while preserving the real mixed-case string in the underlying XML, mirroring the dashboard's CSS text-transform:uppercase rather than literally typing uppercase text). **Vertically BOTTOM-aligned** (not centered) — the M3 column's header is two lines ("M3 ★" + "Design Intent") while the others are one line; bottom-alignment keeps every column's text sharing the same baseline instead of shorter headers floating higher.

Two-line for M1–M5 (main label + small subtitle via break:1, subtitle size 10, also caps): M1/Undesigned, M2/Emerging, M3 ★/Design Intent, M4/Optimized, M5/Leading. "PCF" and the name column are left-aligned; everything else centered. Name-column and PCF-column header cells get the same left padding as data rows (margins left 140).

## 10. Row hierarchy — fill, text, and Pattern-column treatment

| Level | Row fill | PCF text | Name text | M-column text | Δ text | Pattern column |
|---|---|---|---|---|---|---|
| L1 (domain aggregate) | 0D2D4F (navy) | bold 9FC0E8, size 12, left | bold FFFFFF, size 12, appended " · L1 DOMAIN AGGREGATE" | bold C7DBF2, size 12 (M3 cell text turns FFFFFF instead) | bold FFD9A8, size 12 | em dash, color C7DBF2 |
| L2 (process-group avg) | EEF3FA (light blue) | bold black (000000), size 14, left | bold 0D2D4F, size 14, appended " · L2 AVG" | bold 444444, size 14 (M3 cell: fill D6E8FF, text 1B4F8A) | bold B45309, size 14 | em dash, color 444444 |
| L3 | white / F9FBFD alternating stripe | black 000000, size 13, left | 444444, size 14, no indent | 444444, size 14 (M3 cell: fill D6E8FF, text 1B4F8A, bold) | B45309, size 14 | bar — see §11 |
| L4 | white / FBFCFE alternating stripe | black 000000, size 13, left | 444444, size 14, indent = 260 DXA extra left margin (cell margin, not paragraph indent — see note) | same as L3 | B45309, size 14 | colored text badge — see §11 |

Every data cell (all levels) gets thinBorder() (§12). Vertical alignment: PCF and Name columns are TOP-aligned (not centered). Left-aligned cells (PCF, Name) get base left margin 140 DXA; L4 rows add 260 DXA more on top (140+260=400 total) for hierarchy indentation.

Indentation method — cell margins, not paragraph indent. An earlier version used a paragraph-level indent:{left:X}, but Word's rendering of wrapped (multi-line) text with paragraph indent was inconsistent — the wrapped continuation line drifted left instead of staying flush with the first line (confirmed against the dashboard's own correct wrap behavior). Cell margins apply uniformly to every wrapped line with no ambiguity. Always indent via cell margin, never paragraph indent, for this doc type.

## 11. Pattern column — three distinct treatments by level

This is the most important and most-corrected part of the spec. Do not collapse these into one style.

- L1 / L2 (rollup rows): plain em dash (—), no color fill, no bar, no text. Just a colored dash matching the row's text-color scheme.
- L3 (always gets a bar, never text):
  - If the L3 has no L4 children (it's a leaf itself): a solid single-color bar using its own pattern value.
  - If the L3 has real L4 children: a proportionally segmented bar — segment widths proportional to the real count of each pattern among its L4 children, segments divided by a thin white vertical line (size:4, color:FFFFFF) so adjacent segments read distinctly.
  - Bar rendering: a nested single-row table inside the Pattern cell, fixed height 180 twips (HeightRule.EXACT), full width of the cell, no border on the nested bar itself — the outer Pattern cell keeps thinBorder() and is vertically centered with margins (top/bottom 50, left/right 60), so the thin bar sits centered with visible row-stripe-colored space above and below it. This "bar within padding" look is what makes consecutive same-pattern L3 rows visually distinct from each other — do NOT let the fill cover the full cell height, or rows blur together.
  - Bar colors — PATTERN_BAR (medium-tone, dashboard palette): Decision 7B9FD1, Knowledge A79AE0, Document 5EB8E0, Transaction 6FC48C, Exception E88A8A.
- L4 (always gets a colored text badge, never a bar): small bold text, the pattern name itself (e.g. "Knowledge"), size 11, using the dark PATTERN_TEXT palette (Decision 1B4F8A, Knowledge 534AB7, Document 0369A1, Transaction 166534, Exception 991B1B) — on a pale fill background behind it, PATTERN_BADGE_FILL (Decision EEF3FA, Knowledge F3F0FE, Document E0F2FE, Transaction DCFCE7, Exception FEE2E2). This fill+text pairing is the same classic badge convention used in every other doc type in the project. Vertically TOP-aligned (not centered) — matches the row's other top-aligned cells.

## 12. Borders

Two border styles used throughout, no others:

```
function thinBorder() { // every data/header cell
  return { top: {style:SINGLE, size:2, color:'7AAED6'}, bottom: same, left: same, right: same };
}
function noBorder() { // banner, legend, spacer cells, nested bar cells
  return { top: {style:NONE, size:0, color:'FFFFFF'}, bottom: same, left: same, right: same };
}
```
Segment dividers inside a Mixed L3 bar use a special border: NONE top/bottom, SINGLE size:4 color:FFFFFF left/right (the vertical white divider between segments).

## 13. M3 column special highlight (applies at every row level)

Implemented via a shared mCells() helper that special-cases index 2 of the M1–M5 array, rather than duplicating logic per row type:

- L2/L3/L4: fill D6E8FF, text 1B4F8A (NAVY), bold (even though other M-columns at L3/L4 aren't bold).
- L1: stays on the row's navy fill, but text switches from the row's normal C7DBF2 to brighter FFFFFF to stand out.

## 14. Legend (below the table)

Compact, left-packed single row — NOT 5 equal-width columns spread across the full page. Column widths: [1500, 1600, 1600, 1800, 1600] DXA for the 5 items, plus one trailing spacer cell sized to consume the remainder of 13640 DXA.

Each item: a colored square (■, size 13, colored per PATTERN_TEXT — the dark palette) + the pattern name (color 444444, size 13), no border.

Below the legend, one attribution line: "Full L1→L2→L3→L4 hierarchy · Mixed-pattern rows show an equal-weighted rollup of their real L4 children · © Timothy P. King & Claude (Anthropic) 2026" — italic, color 888888, size 13.

## Build/validation checklist for any new domain

1. Extract the domain's JSON (code, name, l1mv, groups[].mv, groups[].l3[] with .mv, .pattern, .mixed, .l4[]).
2. Run `node gen_maturity.js <domain>.json <slug>`.
3. Convert to PDF (soffice --headless --convert-to pdf) and rasterize page 1 + last page for a visual spot check — confirm: banner present, stats cards bordered, two-line ALL-CAPS bottom-aligned headers, PCF column left-aligned + black, name column left-aligned with L4 indent, M3 column highlighted at every level, L3 bars (solid + segmented) render with visible row separation, L4 badges (top-aligned) show pale fill + dark text, legend compact and left-packed with all 5 patterns present.
4. Unzip the output .docx and grep word/document.xml / word/styles.xml to confirm w:jc, w:caps, w:vAlign values and the docDefaults font — never trust a LibreOffice-rendered screenshot alone to settle a styling question; verify in the raw XML.
